# Спецификация трека: Стабилизация ядра, устранение рисков P0/P1 и декомпозиция архитектуры ZIAForge

**Track ID:** `core_safety_and_architecture_20260910`  
**Тип:** `Refactor & Bugfix`  
**Статус:** `In Progress`

---

## 1. Контекст и Проблематика
В ходе совместного глубокого аудита с Codex (`gpt-6-astra`) было выявлено, что частые сбои, потеря текста, зависания UI и ошибки при работе с терминалом вызваны фундаментальными проблемами владения состоянием и архитектурными дефектами ядра:

1. **P0 (Опасность потери данных):** При повторном нажатии "Start" на задаче Electron принудительно удаляет директорию worktree и ветку задачи в Git (`git branch -D`), уничтожая все незакоммиченные файлы пользователя.
2. **P0 (Рассинхрон контекстов):** `selectTask()` в `store.ts` меняет `activeTaskId`, но не синхронизирует `activeRepoId`. Терминал и файловые операции переключаются на чужой проект.
3. **P0 (Небезопасное завершение процессов):** `kill-process-by-command` исполняет `pkill -9 -f "..."` по всей ОС, закрывая посторонние системные процессы.
4. **P1 (Потеря промпта и настроек):** `NewTaskForm` и `store.createTask` обрезают текст задачи до первой строки, а модель, workflow и режим ветки вовсе отбрасываются.
5. **P1 (Запуск шелла вне изоляции):** Фоновый PTY-менеджер запускает шелл в корне репозитория вместо изолированного каталога `worktreePath`.
6. **P1 (Монолит Workspace.tsx):** 4100+ строк в одном компоненте, где смешаны рендеринг, ANSI-парсинг экранов терминала и логика сокетов.

## 2. Цели и Скоуп трека

### В рамках трека:
- Реализовать безопасный запуск задач в `electron/main.ts` без деструктивного удаления веток и рабочих директорий.
- Исправить маршрутизацию в `src/store.ts` с гарантированной синхронизацией `activeRepoId` и изоляцией логов.
- Заменить небезопасный глобальный `pkill` на таргетированное завершение процессов по дереву PID конкретной задачи.
- Обеспечить полное сохранение многострочного промпта пользователя, пресета модели, типа воркфлоу и ветки при создании задачи.
- Гарантировать привязку терминальной сессии задачи к её директории `worktreePath`.
- Провести первичную декомпозицию `Workspace.tsx` и подготовить архитектуру к структурированным потокам событий (JSON streaming) вместо хрупкого эвристического парсера ANSI.

### Вне рамок текущего трека:
- Полная реализация протокола ACP / Codex app-server (будет отдельным треком).
- Подключение внешнего сервера LiteLLM Gateway для фонового авто-ревью (следующий трек).

## 3. Пользовательские сценарии (User Stories)

1. **Как пользователь**, я могу перезапустить задачу или открыть ее заново, не опасаясь, что мои рабочие файлы или ветка будут стерты.
2. **Как пользователь**, я могу переключаться между разными проектами и задачами в сайдбаре, будучи уверенным, что консоль, логи и файлы показывают именно ту задачу, которую я выбрал.
3. **Как пользователь**, я могу ввести длинный подробный промпт с кодом и требованиями при создании задачи, и агент получит его целиком, вместе с выбранной моделью и типом воркфлоу.
4. **Как пользователь**, когда я останавливаю фоновый процесс (например, веб-сервер), останавливается только этот конкретный процесс, без риска убить другие программы на компьютере.

## 4. Критерии приемки (Acceptance Criteria)

- [ ] **AC-1:** Повторный запуск задачи сохраняет существующую директорию worktree и ветку Git.
- [ ] **AC-2:** При вызове `selectTask(taskId)` в `store.ts` значение `activeRepoId` автоматически выставляется в репозиторий этой задачи.
- [ ] **AC-3:** Остановка процесса через IPC завершает только PID целевого процесса задачи без использования невалидированного `pkill -9 -f`.
- [ ] **AC-4:** Объект задачи (`Task`) содержит полное многострочное описание `description`, параметры `model`, `workflow`, `branchType`, `branchName`.
- [ ] **AC-5:** PTY-сессия задачи стартует строго в каталоге `worktreePath`.
- [ ] **AC-6:** Приложение собирается без ошибок (`npx tsc --noEmit` и `npx vite build`), бандл успешно пакуется в DMG.
