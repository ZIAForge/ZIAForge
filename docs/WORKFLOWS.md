# Executable plans

The Plan panel in a real Code or Work task uses a main-process workflow engine. It is separate from the legacy demonstration to-do list. Plans, attempts, verification receipts, review findings and checkpoints are stored privately in the application profile; closing a panel, changing tabs or hiding the window does not stop execution.

## Using a plan

1. Open a Code or Work task and its Plan panel. Select a saved preset, Task selection, or Custom for the coder, independent reviewers and research helpers. The same preset can serve multiple roles or sources; each reviewer/helper still receives a separate context. Custom saves the provider, model, optional API connection, reasoning effort and access selection with the plan. New Code tasks start preparation when Start is pressed, as described below. Work and previously saved plans keep their existing explicit Save/Run behavior.
2. Add ordered steps with instructions and acceptance criteria. New steps depend on the previous step. Choose a verification command, independent review, or both. Commands run in the backend-resolved task directory: a worktree, explicitly selected branch checkout, or Work folder.
3. Save and run. With Auto disabled, each completed step or failed attempt pauses for an explicit Continue. Auto repeats failed attempts within the configured limits and advances after successful steps. A step's Stop after option always creates a checkpoint.
4. Open Agent / approvals to inspect that attempt's real conversation, CLI log and permission cards. Workflow-owned chats accept approval decisions; the plan controls their prompts, context, cancellation and configuration.
5. Pause to stop the current attempt and wait for its owned execution to finish. After full application Quit, the plan remains paused; interrupted attempts require an explicit retry. Completed steps are not repeated.

Completed step definitions cannot be edited or deleted. Add a follow-up step for changed requirements. Pending steps and run policies can be edited while paused. Optimistic revisions reject conflicting saves; a dirty editor retains its draft and requires an explicit reload before running a different saved revision.

## New Code tasks

The five Code choices are real preparation workflows, not three placeholder steps. Start saves a task and its original request before launching its first phase. The description is sent once through the workflow, not again as an ordinary chat message. An uncertain Create acknowledgement retains the same creation identity; retry looks up that task instead of creating another. Startup errors remain visible on the retained task.

| Flow | Preparation and transition | Documents |
| --- | --- | --- |
| Auto | Classify intent and complexity. A repository question may finish with an answer; small and medium changes propose concrete steps. Large changes first pass through requirements, specification and planning. | Optional `answer.md` / `plan.md`; trivial edits need no planning document; large tasks also `requirements.md` and `spec.md`; implementation ends with `report.md`. |
| Fix a bug | Investigate expected/actual behavior and root cause, then propose a scoped fix and regression checks. | `investigation.md`; delivery creates a new investigation version with actual evidence plus `report.md`. |
| Spec first | Inspect the architecture and write a technical design, then propose implementation steps. | `spec.md`, a `plan.md` for complex breakdowns, followed by `report.md`. |
| Requirements first | Requirements → technical specification → concrete implementation plan. Material ambiguity pauses for answers. | `requirements.md`, `spec.md`, `plan.md`, then `report.md`. |
| Multi-model | Scoped explorers → alternative designs → synthesis → plan decision → one implementation with checks → review decision → independent workers and coordinator → decision on findings. | `exploration_N.md`, `plan_draft_N.md`, `final_plan.md`, `implementation_report.md`, `review_diff.patch`, worker JSON and `final_review.md`; an authorized correction produces `fix_report.md`. Later explicit cycles use numbered reports. |

The user selects saved presets or Custom independently for planning, coding, review and correction. The same model may serve different roles with separate conversations. Existing multiple-reviewer/helper settings remain available in the Plan panel. Review can be disabled explicitly; implementation then requires executable verification. No cloud-only provider is selected implicitly.

Preparation agents return a bounded `ziaforge-phase` JSON result containing questions, document contents and proposed steps. They are instructed not to change source; collected workspace fingerprints reject preparation that does. This detection is not a filesystem sandbox. The backend validates the phase, assigns identities, writes the actual documents and updates the structured checklist. The checklist is authoritative; a model cannot mark implementation complete by editing a Markdown file. Each phase has a fresh conversation with the task request, shared context, previous documents and saved answers.

Every proposed executable plan is shown before acceptance, including exact verification executable/arguments and the task workspace. Auto never bypasses questions, plan approval or Multi-model findings, including trivial/small changes without verification commands. Manual mode also pauses after successful phases/steps. Request changes generates a new proposal/document version; approval applies only to the displayed gate, plan revision and unchanged document hashes. Closing a panel, switching tasks or restarting does not approve anything.

### Forge discussion and foundation revisions

New Code plans enable the versioned Forge discussion. The task opens a persistent **Forge · Discussion** tab; native phase/worker conversations and CLI logs remain accessible through Execution / logs. A short initial idea is enough to start requirements discovery. Important product choices and technical choices are discussed across multiple turns; a counterquestion, missing answer, or request for advice is not agreement. Existing repository facts and explicitly delegated decisions avoid unnecessary questionnaires.

The discussion retains original questions, choices, answers and amendments across provider sessions and application restarts. Send a clarification at any stage. During an active run the engine first interrupts and drains its owned attempt before discussing new input. Sending text does not approve a document or authorize implementation. Stop remains a separate control. Drafts and uncertain command acknowledgements retain their identity so a retry cannot silently send twice.

Requirements and Technical Specification have document acceptance checkpoints. Open the retained Markdown, request a revision or edit the latest document, then explicitly accept its exact version. A model's `ready` output is a proposal, not human acceptance. Document acceptance remains necessary with automatic continuation enabled. Spec-first can present a combined specification/implementation proposal, with the document hashes bound to that approval.

The proposed implementation checklist can be edited, extended and reordered before acceptance, including its real verification commands. Approval authorizes only those displayed steps against the accepted foundation. An explicit return to Requirements, Technical Specification or Planning starts a new foundation revision and invalidates dependent approvals. Completed implementation/check/review evidence remains in history; superseded unfinished stages and their chats remain retained. Subsequent implementation must pass a fresh plan decision. New requirements do not retroactively certify earlier code, and previously completed steps are not silently rerun or rewritten.

Implementation can also stop with consequential questions instead of being marked complete. Answer the checkpoint to continue its accepted scope, or send a new requirement for replanning. The host does not run Green verification or accept a review as proof of implementation while that question remains unresolved.

Saved older Code plans keep their retained behavior until the user explicitly opens and sends into Forge discussion. Work uses its separate engine and is unaffected. The selected planner/executor, presets and Custom model/access/effort settings remain visible; independent reviewers and helpers remain in Plan and roles. Settings already bound to completed verified implementation retain their existing lock.

New Multi-model plans persist each explorer, designer, synthesis and reviewer session. Two scoped explorers and three designers are used by default; Roles allows one to six explorers, one to three designers and a custom coordinator. Designers receive verified artifact paths instead of duplicated exploration bodies. The synthesized final plan contains one whole-task implementation pass. Completed malformed stage output permits one format repair; uncertain transport delivery pauses without an automatic resend.

Multi-model writes an implementation report before review. Workers share one complete immutable patch; the coordinator checks and deduplicates their findings against source. Explicitly configured reviewer findings remain mandatory. Custom review policy takes priority over automatic size/risk selection; an ambiguous automatic decision presents a choice. An empty actual patch skips reviewer inference with an explicit reason.

Blocking findings require explicit authorization for one fresh correction, followed by real checks and a numbered fix report. Correction does **not** automatically launch another review. Approved suggestions pause for acknowledgment without an unwanted fix or extra model call. Comments request coordinator reconsideration using retained worker results. After completion, Review again starts an explicit review cycle; prior checks are reused only when source and implementation identity still match. A completed Git publication requires a follow-up task instead. Saved legacy plans retain their previous review behavior.

Real phase and worker chats appear in the task even while Plan is closed. Follow stage selects the current conversation; manually opening or closing another tab stops following without discarding drafts. Closed phase chats remain in the task's Recent list. Documents appear in the Plan panel and open as Markdown. Immutable versions are stored in the registered project's `artifacts/worktrees/<taskId>/code-flow/<stepId>/<attemptId>/`. Their receipts include hash, size, version and producing attempt; changed, missing or substituted files cannot be approved as the retained version. Artifacts are outside the code worktree and do not silently enter Git commits. Final delivery reports use real completed implementation/check/review receipts. Git finalization remains governed by the existing explicit policies and refuses workspace changes since verification.

## Verification, review and TDD

Verification commands are entered by the user or accepted from a new Code plan proposal. The step editor accepts a shell command and represents it as `/bin/sh -lc <command>` with a 60-second timeout. The backend contract also supports explicit executable/argv and bounded timeouts. Model output alone cannot authorize a command or certify its result. An exit-zero result requires verified process cleanup; timeout, cancellation, excessive output and cleanup failure are failures.

Each command produces an immutable request and receipt with command, canonical cwd, exit code/signal, output files, limits and a source fingerprint. Captured output and process lifetimes are bounded. A small owned process-group supervisor remains alive until ordinary descendants are cleaned up. This is process supervision, not an OS sandbox; deliberately daemonized processes that escape the group are outside that guarantee.

For TDD, configure a Red check. The coder first writes the failing test, the command must actually fail normally, and only then may implementation and Green verification proceed. A missing executable, timeout or cleanup failure is not a valid Red result. Successful Red evidence is bound to the step definition and cannot be reused after changing that definition.

Review uses an independent provider session with the requirement, implementation report, actual receipts and bounded Git/file evidence. Reviewer output must satisfy a strict structured verdict; blocking findings cannot coexist with approval. A rejected or malformed review creates a failed attempt. The next attempt receives the failure evidence, and verification and review run again. Code/source fingerprints fence changes during verification or review so an old result does not certify newer files.

Reviewer/helper roles restrict Codex to `read-only` with no escalation, Claude to native plan mode and the API adapter to read tools, regardless of the selected preset's broader access. Claude plan mode is a provider tool policy, not an operating-system sandbox. Antigravity is also available for these roles: ZIAForge forces `CLI settings` with terminal sandboxing and never inherits unrestricted access from the preset. This is **not filesystem read-only enforcement**. Its review/helper prompt prohibits changes, and workspace fingerprint checks reject a result when files changed. These checks detect changes in the collected task evidence; they do not prevent or undo filesystem writes, or certify access outside the task workspace.

Default circuit breakers stop after three failed attempts on a step or fifty total attempts. Counters and reasons persist across application restarts. Pausing/interruption consumes an attempt but not a failed-attempt count. The current GUI displays the defaults; the validated plan contract bounds custom limits. Retry does not reset counters.

## Storage and scope

The canonical plan and state live in `userData/workflows/plans/<taskId>/workflow.json`. Application-owned state is written atomically with private permissions and fsync before notifications. Verification evidence lives under `userData/workflows/verification/`. Native conversation journals retain separate session/run identities. Damaged or inconsistent workflow state is rejected and retained for recovery rather than overwritten with invented success.

## Multiple reviewers, helpers and Git policies

A plan may name up to eight reviewers and four helpers, including repeated presets with distinct source identities. Every required source must approve; the policy is `all`, not a majority vote that can discard a blocking finding. Each source retains its own session, configuration, verdict, error and source fingerprint. Research helpers run before implementation and contribute bounded context without certifying success. Completed reviewer results can be reused after interruption only while their saved source identity, configuration and verified input fingerprint still match; changed files require fresh evidence.

Git commit, merge and push default to manual. A saved plan can explicitly enable individual `after-plan` policies with a target branch/remote. The engine finalizes only the whole verified plan, after its configured final checkpoint; Auto does not imply blanket permission to publish. Source/HEAD/index fingerprints and immutable operation IDs guard the transition. GitService freezes selected reviewed bytes, preserves unrelated staged changes, refuses ignored-file overwrites during branch switches, and records each command outcome. Failure or an uncertain interrupted mutation blocks publication and preserves receipts; restart is not permission to repeat an unknown result. A remote push still requires the user's existing Git authorization and a configured remote.

Work tasks use ordinary registered folders and artifact templates without requiring `.git`; Git finalization is unavailable there. The [local CLI dispatcher](CLI.md) starts/pauses the same saved engine, and [API connections](API_CONNECTIONS.md) use explicit endpoint selections. Generated prompts restrict work to the current step. These are source implementation contracts; final GUI, native inference, both-architecture and packaged-release claims require evidence for the exact artifact.
