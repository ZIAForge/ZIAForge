`task.status === 'running'` разрешает запуск PTY и добавляет плашку задачи в
`activeProcesses` на строке 4153. В `store.ts` этот статус выставляется после
подготовки рабочей папки; он не означает непрерывную генерацию модели.
Плашка процесса и оранжевый индикатор задачи имеют собственный смысл и не
вычисляют `Composer.isRunning`. Ошибки выбора идентификатора новой вкладки или
отсутствия её PTY-вывода в детекторе в проверенном коде не обнаружено.

Основная подтверждённая ошибка находилась в переходах `AgentActivity.output()`.
После завершения boot любой изменившийся экран, для которого `hasIdlePrompt()`
вернул `false`, переводил сессию в `generating`. При пошаговой перерисовке CLI
временно стирает строку ввода, затем выводит баннер и footer отдельными пакетами.
Отсутствие промпта на промежуточном экране ошибочно принималось за работу агента.

Минимальная последовательность, воспроизводящая этот дефект без отправки запроса:

```ts
activity.boot('chat')
activity.output('chat', '> ')
activity.output('chat', '\x1b[H\x1b[JAntigravity CLI 1.2.1\r\n')
// Исходный isRunning('chat'): true. Исправленный: false.
```

Вторая ошибка: `isRunning()` включал `pending.size > 0` и `queued`, а
`startTurn()` немедленно устанавливал `generating` ещё до ответа CLI.
Следовательно, очередь и незавершённый IPC-запрос были достаточны для появления
кнопки даже при корректно распознанном idle. `boot()` сохраняет pending/queued
для продолжающейся доставки сообщений. У нового уникального ID они изначально
пусты; это не объяснение появления очереди в совершенно нетронутом чате, а
отдельный дефект контракта `isRunning`.

Третья группа ошибок обнаружена в `terminalScreen.ts`. Существующая запись agy
содержит `CSI ? 2026 $ p`, `CSI = 1 ; 1 u` и `CSI ? u`. Старый разбор CSI не
поглощал всю последовательность с промежуточными/private-байтами: в экран мог
попадать текст `p` или `1;1u`, а private-команда `?u` ошибочно восстанавливала
сохранённую позицию курсора. Это искажает экран, на котором работает
`hasIdlePrompt()`. Например, `> ` с последующим `CSI ? 2026 $ p` превращался для
парсера в `> p`: такой промпт уже не распознавался, и исходный детектор оставался
в `generating` до следующего подходящего вывода. OSC со строковым терминатором
точно на границе пакета также ошибочно оставался в `trailing`.

Разбор исправлен так, чтобы поглощать параметры, промежуточные байты и финальный
байт CSI полностью; неподдерживаемые private-команды не печатают текст и не
вызывают обычную команду с тем же завершающим символом. Завершённый OSC больше
не сохраняется как незавершённый. Такое разделение управляющих и печатных байтов
соответствует описанию [XTerm Control Sequences](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html).

Сам статический footer с `>`, разделителями, `? for shortcuts` и
`Gemini 3.8 Flash · high` распознавался в исходном коде. Имеющаяся запись запуска
также завершалась корректным idle ещё до исправления. Поэтому по одному
скриншоту нельзя честно установить, какой именно пакет или незавершённая доставка
включили кнопку в том пользовательском окне. Подтверждены достаточные для
ложного Stop ошибки; точное состояние исходного окна остаётся непроверенным.

Теперь переходы имеют следующий смысл:

| Состояние/событие | `isBusy` | `isRunning` / кнопка Stop |
| --- | --- | --- |
| Запуск и авторизация CLI | Да | Нет |
| Очередь или незавершённая отправка без генерации | Да | Нет |
| Запрос отправлен, ожидается вывод | Да (`awaiting`) | Нет |
| Распознан `Generating...`, `Generating…`, `Thinking...`, `esc to cancel/interrupt` | Да | Да |
| Спиннер Брайля в отправленном ходе | Да | Да |
| Незавершённая надпись рядом со спиннером при нетронутом запуске | Да | Нет |
| Ожидание ответа на запрос разрешения | Да | Нет |
| Свежий промпт после ответа/отмены, очередь пуста | Нет | Нет |
| Обычная перерисовка баннера или footer в idle | Нет | Нет |

Фаза `awaiting` отделяет отправку от наблюдаемой генерации. Авторизация исключена
из признаков генерации; отдельно проверено даже разбиение всей записи на
одиночные символы. После подтверждённого начала ответа обычные части текста не
сбрасывают генерацию, свежий промпт завершает её. Новая отправка во время уже
подтверждённой генерации не скрывает кнопку. Нумерованный ответ не считается
меню разрешений без признака интерактивного вопроса. Таймеров, объявляющих CLI
idle просто из-за отсутствия текста, в продуктовый код не добавлено.

В проверке настоящего PTY исходный и исправленный детекторы одновременно
получали один поток. Из 45 обработанных пакетов 38 пришлись на нетронутый запуск
и idle. Исходный детектор дал один переход в ложную генерацию при промежуточной
перерисовке; исправленный — ноль. Затем прошли запрос `long-generation`, появление
генерации, Ctrl+C, возврат к промпту и второй запрос `Привет`. Все события
зарегистрированы с одним PID, перезапуска процесса не было. Это проверка живого
PTY с воспроизведением записанного вывода и детерминированными ответами локального
CLI; она не выполняет авторизацию или запросы к сервису модели.

В React integration-тесте дополнительно проверена вся цепочка: основная задача
остаётся `running`, её сессия генерирует, пользователь нажимает «Новый чат», все
35 пакетов запуска попадают в callback именно нового чата, кнопка остаётся
скрытой на каждом шаге, пользовательских отправок нет. Возврат к основной
вкладке снова показывает её активную генерацию. Прежние проверки отмены и
повторной отправки сохранены; теперь они подают признаки реальной генерации
перед нажатием Stop. Отмена ещё не начавшего генерировать запуска проверяется
через существующую кнопку завершения процесса в плашке задачи.
