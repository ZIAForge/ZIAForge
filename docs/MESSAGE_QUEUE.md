# Message queue

While a chat is generating, **Send** remains disabled and **Stop** still interrupts only its current turn. Use the separate **Queue** button to save the next message. The backend acknowledges only after durable storage; accepting a queued message is not confirmation that the provider has received or answered it. Queues are scoped to one task/chat and remain separate from conversation history and the editable draft.

The visible list shows waiting and dispatching items. Waiting messages run in order when the queue is enabled and the provider is ready. **Pause queue** holds remaining messages without interrupting an already active turn; **Continue queue** explicitly enables delivery. You can cancel a waiting item. A dispatching item cannot be cancelled as if it had never been sent.

Stop, ending the session and full application Quit pause queued work. After restarting, **Resume** restores the native/local conversation only; it does not continue the queue or send the draft. Inspect the saved list, resume the conversation, then choose **Continue queue**. Changing the model, provider or preset is blocked until queued messages are finished or removed. Workflow-owned chats remain controlled by their plan and expose no manual queue commands.

A failed or lost save acknowledgement retains a separate pending queue ID and the original text. **Retry queue save** checks that same request safely. It does not queue newer text typed in the meantime; that text remains in the composer. Ordinary Send stays disabled until the save is confirmed, preventing a second delivery through a different message ID. No draft is cleared before acknowledgement, and a late acknowledgement clears only its matching unchanged draft. Empty text, messages over 100,000 characters and text containing NUL are rejected before retaining a pending queue ID, so the draft remains editable without blocking the chat. Invalid pending content from an older draft cache is also released; valid attempts with an uncertain acknowledgement keep their identity.

If a crash or transport failure makes delivery **uncertain**, the item stays paused and is never resent automatically. Check the visible history and the provider's outcome. You may manually copy its text, then **Remove from queue**. Removal records dismissal; it does not retract an already delivered prompt and does not retry it. Submit a copied message only as a deliberate new request after resolving that uncertainty. Restoring an older queue backup marks its retained items uncertain for the same reason; restoration is not permission to execute them again.

Queue documents use private atomic storage and validated recovery backups. Size/count limits and corruption errors are visible; damage is not converted into an empty queue. Session history, queue receipts and screenshots can contain prompts and are private diagnostic material. Deterministic tests verify persistence, order, cancellation and restart; fixture success does not certify a live provider account or a packaged build by itself.
