# Native CLI conversations on macOS

ZIAForge starts locally installed command-line clients using their existing native login. Configure a saved preset in Settings, register a project using the folder picker, then create a Code task with that preset. New managed Code tasks send the initial description once when Start launches preparation; Save draft does not contact a model. Ordinary free-chat drafts remain unsent until Send. No ZIAForge API key is required for these transports. This document's native version gates were verified on macOS; other platform/package checks remain separate evidence.

| Provider | Compatibility gate | Transport | Permissions | Stop |
| --- | --- | --- | --- | --- |
| Codex | `0.153.x`, patch 4 or later | App Server stdio | Read only / Workspace write with interactive approval; explicit full access | Interrupt current turn |
| Claude Code | `2.1.114` | Persistent stream-json with initialize/control messages | Native default approval; Read only maps to native plan mode; explicit bypass | Interrupt current turn |
| Antigravity | `1.2.2`, `1.2.7` | Persistent headless stream-json | CLI settings adds the native terminal sandbox and inherits native tool policy; explicit unrestricted mode | Native SIGINT, terminal result, owned cleanup and reconnect to the same conversation |

An unrecognized CLI version fails before sending the prompt and preserves the draft. A missing CLI or native authentication error is shown in the chat. Sign in using the provider's own CLI. ZIAForge does not edit global provider permission settings or extract credentials. Model availability and subscription limits remain controlled by the installed client/account.

Claude's plan mode is a native tool-permission mode, not an operating-system filesystem sandbox. Antigravity's headless protocol does not provide interactive approval messages. Stop uses native SIGINT: the adapter waits for an interrupted terminal result and close, verifies owned-process cleanup, then starts a new process for the same saved conversation before another send. Its `--mode=plan` cannot enforce read-only access, so Read only and Workspace write presets are rejected rather than weakened. CLI settings does not promise read-only file access; its sandbox applies to terminal commands. If interruption or cleanup cannot be confirmed, the session reports failure and preserves the draft/history. Explicit End session remains separate from Stop. Resume starts another process for its saved native conversation.

All three transports use backend-owned processes, journalled events and the same conversation UI. Reload, Settings, tab close/reopen and macOS window hide/reopen preserve a live conversation. Acknowledging Stop does not complete a turn: Send stays disabled until the matching terminal event arrives. File attachments are currently unavailable. Antigravity can display final tool output but does not advertise streamed tool output or thinking.

### Task directory and native workspace

The task directory comes from the backend's registered project/worktree, never from a renderer path or a fallback to the home directory. Antigravity needs both the process working directory and an explicit `--add-dir <task-directory>` on every launch, including conversation resume and reconnect after Stop. Its `init.cwd` describes the CLI process directory; it does not by itself establish the agent's tool workspace. ZIAForge also sets the child `PWD` to that directory and rejects missing or mismatched initialization before accepting user input.

This fixes a defect in 0.0.8: the process could start in the correct worktree while the native conversation had no workspace, causing tools to operate from the home directory. Old chat history is preserved; resuming the conversation supplies the explicit workspace binding. The [native project documentation](https://antigravity.google/docs/projects/) distinguishes the conversation's project from the process directory, and the installed CLI help documents `--add-dir`.

A working directory is not a filesystem sandbox. Explicit unrestricted permissions still permit access outside that directory. ZIAForge does not silently change the selected permission policy or global CLI settings. Use the provider's available restricted policy when broader access is not intended; the supported permission boundaries are listed above.

After a full application Quit or provider exit, history remains visible and **Resume session** explicitly reconnects to the saved native conversation. It never silently resends a prompt whose delivery is uncertain. An empty conversation that has never received input may start a fresh native context, because providers need not persist empty rollouts. If an older session has no native reference, choose chat settings explicitly to continue using a bounded history handoff. Missing or corrupt references never resume an unrelated conversation.

The controls beside the attachment button at the bottom of the Composer select a saved preset or **Custom**. Custom exposes CLI, model and options for permissions and reasoning effort; **Create preset** saves a reusable configuration without leaving the conversation. Apply is allowed when the session is idle; finish or stop an active turn first. Choosing a different CLI retains the entire visible history and sends bounded recent conversation excerpts with the next message; it does not claim to migrate private provider context. Same-provider continuation uses native resume where available. Editing a saved preset elsewhere does not silently change a running chat. A failed change keeps the draft and exposes the authoritative session state for recovery.

Sending keeps the text field editable for the next draft. A pending send cannot be submitted twice, and its acknowledgement does not clear newer text or take focus from another control. Typing a new draft alone never submits it. The separate queue action remains deliberate.

**CLI logs** display a bounded in-memory view of actual stdout/stderr and lifecycle messages with best-effort credential redaction. They are separate from the structured conversation and ordinary shell terminal. They reset after a full application restart and are not automatically copied into the global diagnostic log or an external report.

The **Prefer native Claude executable** application setting is enabled by default. If PATH points to a script and an adjacent `claude.real` exists, ZIAForge checks its native executable format and supported version before choosing it. An invalid native candidate produces an error instead of silently falling back. Without a native sibling, the PATH command remains available and the CLI log identifies it as a script or wrapper. Disable this preference to deliberately use the PATH command. No global CLI configuration or authentication is changed.

Model catalogs use native supported interfaces: Codex App Server `model/list` follows every page including hidden entries; Claude uses initialization metadata; Antigravity uses its model listing. Returned models are not a guarantee that the current account can execute them. Manual model IDs remain an explicit choice when discovery is unavailable; no fixed model-count promise is embedded in the app.

Reasoning effort travels with the preset or explicit task/chat selection, including full application restart. **Provider default** is distinct from the explicit `none` token. Codex advertises per-model supported efforts and a default through [`model/list`](https://learn.chatgpt.com/docs/app-server); ZIAForge preserves that metadata and supplies the selected effort to `turn/start`. It does not assume that every model supports `ultra`, or that `max` is interchangeable with `xhigh`. An explicitly entered model without metadata can use a manual effort token, whose acceptance remains the CLI's responsibility. The verified Claude Code `2.1.114` flag accepts `low`, `medium`, `high`, `xhigh` and `max`; Antigravity `1.2.7` accepts `low`, `medium` and `high`. Explicit Antigravity effort requires `1.2.7`; the retained `1.2.2` transport is available with the provider default. Chat Completions connections use `reasoning_effort`; explicitly selected Responses connections use `reasoning.effort`, subject to their server's support.

Workflow execution uses the selected role's effort. Reviewer and helper permissions remain read-only even when their source preset permits writes; an effort change never grants additional access.

Codex `0.153.4` rejects `config.model_reasoning_effort: null`; omitting a turn override can retain the previous native effort. An explicit **Provider default** therefore resolves the actual thread model through `model/list` and applies its advertised default on every turn. If a manually entered model has no advertised default, this reset fails visibly instead of claiming that the previous setting was cleared. A configuration that never selected an effort continues to inherit the client's ordinary defaults.

Executable plans implement step execution, verification receipts, multiple independent reviewers/helpers, bounded repair attempts, checkpoints, Work folders, explicit Git policies and restart recovery. See [executable plans](WORKFLOWS.md), [API connections](API_CONNECTIONS.md) and the [local CLI](CLI.md). These source capabilities remain distinct from release certification.
